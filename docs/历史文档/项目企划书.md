# 全日制学校排课系统 - 项目企划书

## 一、问题分析与定义

### 1.1 核心问题描述

排课问题本质上是一个**多维度资源分配问题**，需要在满足硬性约束的前提下，尽可能优化软性约束，将以下四个核心要素进行合理匹配：

```
┌─────────────────────────────────────────────────────────┐
│                    排课四要素                            │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐    │
│  │  时间   │  │  教师   │  │  班级   │  │  课程   │    │
│  │ (When)  │  │ (Who)   │  │ (Where) │  │ (What)  │    │
│  └────┬────┘  └────┬────┘  └────┬────┘  └────┬────┘    │
│       │            │            │            │          │
│       └────────────┴─────┬──────┴────────────┘          │
│                          ▼                              │
│                   ┌──────────────┐                      │
│                   │   课程表     │                      │
│                   │  Schedule    │                      │
│                   └──────────────┘                      │
└─────────────────────────────────────────────────────────┘
```

### 1.2 问题复杂度分析

排课问题属于 **NP-Hard** 问题，其复杂度来源于：

| 维度 | 数量级示例 | 组合爆炸 |
|------|-----------|---------|
| 时间槽 | 5天 × 8节 = 40个 | - |
| 班级数 | 6年级 × 4班 = 24个 | - |
| 教师数 | 约50人 | - |
| 课程数 | 约15门 | - |
| **理论搜索空间** | | **≈ 10^100+** |

因此，穷举法不可行，必须采用启发式算法或约束传播技术。

## 二、约束条件体系

### 2.1 硬性约束（Hard Constraints）- 必须满足

硬性约束是**不可违反**的规则，违反则课表无效：

```
┌─────────────────────────────────────────────────────────┐
│                    硬性约束体系                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  【时间冲突约束】                                        │
│   H1: 同一教师在同一时间只能上一节课                      │
│   H2: 同一班级在同一时间只能上一节课                      │
│   H3: 同一教室在同一时间只能容纳一个班级（如有教室限制）    │
│                                                         │
│  【教学计划约束】                                        │
│   H4: 每个班级的各科目周课时数必须满足教学计划             │
│   H5: 连堂课必须安排在连续的时间槽                        │
│                                                         │
│  【教师可用性约束】                                      │
│   H6: 教师只能在其可用时间段内安排课程                    │
│   H7: 早班/晚班教师的时间范围限制                        │
│                                                         │
│  【特殊课程约束】                                        │
│   H8: 某些课程只能安排在特定时间（如体育课避开正午）        │
│   H9: 实验课必须安排在实验室可用时间                      │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 2.2 软性约束（Soft Constraints）- 尽量满足

软性约束是**优化目标**，违反会降低课表质量但不致无效：

```
┌─────────────────────────────────────────────────────────┐
│                    软性约束体系（带权重）                 │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  【教师体验优化】                           权重         │
│   S1: 教师每天课程尽量集中，减少"空窗期"     ████████ 8  │
│   S2: 教师每天课时数相对均衡                 ██████ 6    │
│   S3: 同一教师的课尽量不要连续太多节         █████ 5     │
│   S4: 教师跨年级教学时，相邻课程楼层接近     ████ 4      │
│                                                         │
│  【学生学习优化】                                        │
│   S5: 主科（语数外）尽量安排在上午           ████████ 8  │
│   S6: 同一科目不宜连续安排（除连堂外）       ███████ 7   │
│   S7: 一天内同科目最多出现次数限制           ██████ 6    │
│   S8: 体育课后不宜紧接需要高度集中的课程     █████ 5     │
│                                                         │
│  【整体均衡优化】                                        │
│   S9: 班级每天课程难度均衡分布               █████ 5     │
│   S10: 平行班的相同科目尽量同步              ████ 4      │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 2.3 您提到的特殊约束处理方案

| 特殊问题 | 约束类型 | 处理策略 |
|---------|---------|---------|
| **平行分班** | 软约束 | 同年级同科目尽量安排在相同时间槽，便于教研和考试 |
| **教师早晚班** | 硬约束 | 为每位教师设置可用时间窗口，算法只在窗口内分配 |
| **课程连堂** | 硬约束 | 将连堂课视为一个"超级课程单元"，占用连续时间槽 |
| **教师跨年级** | 软约束 | 优化教师在不同年级间的课程时间分布，减少奔波 |
| **教师较少** | 隐式约束 | 提高资源利用率，优先处理"瓶颈"教师（任课多的教师） |

## 三、数学建模

### 3.1 决策变量定义

采用**0-1整数规划**模型：

```
定义决策变量 X[t][c][s][r] ∈ {0, 1}

其中：
  t ∈ T : 教师集合 (Teachers)
  c ∈ C : 班级集合 (Classes)  
  s ∈ S : 时间槽集合 (Slots)，s = (day, period)
  r ∈ R : 课程集合 (Courses)

X[t][c][s][r] = 1 表示：教师t 在时间槽s 为班级c 上课程r
X[t][c][s][r] = 0 表示：不安排此课
```

### 3.2 约束条件数学表达

**硬性约束的数学形式：**

```
【H1】教师同一时间只上一节课：
∀t ∈ T, ∀s ∈ S: Σ(c,r) X[t][c][s][r] ≤ 1

【H2】班级同一时间只有一节课：
∀c ∈ C, ∀s ∈ S: Σ(t,r) X[t][c][s][r] ≤ 1

【H4】满足周课时计划：
∀c ∈ C, ∀r ∈ R: Σ(t,s) X[t][c][s][r] = Plan[c][r]
（Plan[c][r] 表示班级c的课程r每周应有课时数）

【H5】连堂约束：
若课程r需要连堂，则 X[t][c][s][r] = 1 时，必须有 X[t][c][s+1][r] = 1

【H6】教师可用性：
∀t ∈ T, ∀s ∉ Available[t]: Σ(c,r) X[t][c][s][r] = 0
```

### 3.3 目标函数

```
最小化总惩罚值：

Minimize: Σ (Wi × Vi)

其中：
  Wi = 第i个软约束的权重
  Vi = 第i个软约束的违反程度（量化值）

例如：
  V1 = Σt（教师t的空窗期数量）
  V5 = Σ（主科安排在下午的次数）
  ...
```

## 四、算法设计

### 4.1 算法选型分析

| 算法类型 | 优点 | 缺点 | 适用场景 |
|---------|------|------|---------|
| **回溯+剪枝** | 能找到精确解 | 大规模时太慢 | 小型学校 |
| **贪心算法** | 速度快 | 解质量不稳定 | 快速生成初始解 |
| **遗传算法(GA)** | 全局搜索能力强 | 参数调优复杂 | 中大型问题 |
| **模拟退火(SA)** | 易于实现，效果好 | 收敛慢 | 中型问题 |
| **约束传播+回溯** | 高效剪枝 | 实现复杂 | 约束紧的问题 |
| **混合策略** | 综合优势 | 设计复杂 | **推荐方案** |

### 4.3 关键算法细节

#### 4.3.1 贪心构造策略

```
优先级评分函数 Priority(课程任务) = 
    w1 × 是否连堂课 +
    w2 × 任课教师剩余可用时间槽数量的倒数 +
    w3 × 该课程的特殊时间约束数量 +
    w4 × 该班级已排课程密度
```

#### 4.3.2 遗传算法编码方案

```
染色体编码：课程任务的排列顺序
┌─────────────────────────────────────────┐
│ [任务3][任务1][任务7][任务2]...[任务N]  │
└─────────────────────────────────────────┘
           ↓ 解码
按顺序贪心分配时间槽 → 得到完整课表

优势：
• 保证解码后一定得到"可行解"（或接近可行）
• 交叉、变异操作简单
• 避免了直接编码课表的高维度问题
```

## 七、技术选型建议

### 7.1 技术栈推荐

| 层次 | 推荐方案 | 备选方案 | 理由 |
|------|---------|---------|------|
| **前端** | Vue 3 + Element Plus | React + Ant Design | 组件丰富，适合管理系统 |
| **后端** | Python + FastAPI | Node.js + Express | Python生态对算法支持好 |
| **算法库** | DEAP (遗传算法) | OR-Tools | 易于定制，文档完善 |
| **数据库** | SQLite / PostgreSQL | MySQL | 轻量级部署或生产环境 |
| **数据处理** | Pandas + NumPy | - | 矩阵运算效率高 |

## 十、总结

### 10.1 核心设计理念

1. **约束分层**：区分硬约束和软约束，确保解的可行性优先
2. **算法混合**：结合多种算法优势，分层解决问题
3. **可扩展性**：支持自定义约束，适应不同学校需求
4. **人机协作**：自动排课 + 手动微调，兼顾效率与灵活性

### 10.2 预期成果

- ✅ 自动生成满足所有硬约束的课表
- ✅ 软约束满足率目标 > 85%
- ✅ 单次排课时间 < 5分钟（中等规模学校）
- ✅ 支持手动调整与冲突实时检测
- ✅ 多种格式导出（Excel、PDF、打印）

### 10.3 下一步行动

1. 确认本企划书中的约束条件是否完整覆盖您学校的实际需求
2. 提供示例数据（或虚拟数据）进行算法验证
3. 确定技术栈选择
