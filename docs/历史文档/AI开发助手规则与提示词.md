# AI 开发助手规则与系统提示词

> 本文档总结了排课系统开发过程中的经验教训，形成一套针对 AI 助手的规则和提示词模板。
> 
> 适用于：Cursor AI、ChatGPT、Claude 等大语言模型辅助开发场景。

---

## 一、核心原则

### 1.1 黄金三角法则

```
            【先诊断】
               ▲
              / \
             /   \
            /     \
【不假设】 ◀─────────▶ 【验证后行动】
```

1. **先诊断，后行动**：遇到问题时，先查看日志和错误信息，确定根本原因后再修改代码
2. **不做假设**：不假设代码会按预期工作，不假设数据库已同步，不假设 API 参数正确
3. **验证后行动**：每次修改后验证效果，而不是批量修改后一起测试

### 1.2 问题诊断优先级

```
┌─────────────────────────────────────────────────────────────────┐
│   当前端出现问题时，按以下顺序诊断：                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   1. 先看后端终端日志     ← 80%的问题根源在这里                 │
│   2. 再看浏览器 Network   ← 确认请求/响应状态                   │
│   3. 然后看控制台错误     ← 前端渲染问题                        │
│   4. 最后看代码逻辑       ← 确认上下游无误后再看                │
│                                                                 │
│   关键洞察：                                                    │
│   • CORS 错误 ≠ CORS 配置问题（通常是后端崩溃）                │
│   • 422 错误 = 参数校验失败（检查请求参数）                     │
│   • 500 错误 = 后端代码异常（检查后端日志）                     │
│   • 显示 Mock 数据 = API 请求失败（确认后端运行正常）           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 二、代码修改规范

### 2.1 修改前必做清单

```markdown
□ 1. 阅读相关文件，理解现有逻辑
□ 2. 确认要修改的具体位置
□ 3. 评估修改可能影响的其他部分
□ 4. 如涉及数据库，确认表结构是否需要同步
□ 5. 如涉及 API，确认前后端参数约定
```

### 2.2 数据库变更规则

```
╔═══════════════════════════════════════════════════════════════════╗
║                    数据库变更铁律                                  ║
╠═══════════════════════════════════════════════════════════════════╣
║                                                                   ║
║   修改 ORM 模型 ─────────┬────────▶ 必须同步数据库               ║
║                          │                                        ║
║                          ├─ 方案A: 使用 Alembic 迁移              ║
║                          │         alembic revision --autogenerate║
║                          │         alembic upgrade head           ║
║                          │                                        ║
║                          ├─ 方案B: 手动 SQL                       ║
║                          │         ALTER TABLE xxx ADD COLUMN ... ║
║                          │                                        ║
║                          └─ 方案C: 临时兼容层（紧急情况）         ║
║                                    在 API 层添加默认值             ║
║                                                                   ║
║   ⚠️  警告：ORM 模型与数据库不同步会导致 500 错误               ║
║            表现为 CORS 错误（实际是后端崩溃）                     ║
║                                                                   ║
╚═══════════════════════════════════════════════════════════════════╝
```

### 2.3 前后端联动修改

当一个功能涉及前后端时，按以下顺序：

```
1. 明确数据流向
   用户操作 → 前端 API 调用 → 后端路由 → 业务逻辑 → 数据库

2. 从数据源开始修改
   数据库表 → ORM 模型 → Schema → CRUD → Router → 前端 API → 前端组件

3. 每层修改后验证
   - 数据库：SELECT 验证数据
   - 后端：Swagger UI 或 curl 测试 API
   - 前端：浏览器开发者工具验证
```

## 三、常见问题解决模式

### 3.1 数据不显示

```javascript
// 诊断步骤
console.log('1. API 响应:', response)           // 确认 API 返回数据
console.log('2. 解析后:', data.items)            // 确认数据解析正确
console.log('3. 绑定数据:', dataList.value)      // 确认响应式绑定
// 检查模板 v-for 的变量名是否正确
```

**常见原因：**
- API 返回 500 错误，fallback 到 Mock 数据
- 字段名不匹配（后端 `snake_case` vs 前端 `camelCase`）
- 异步加载时机问题

### 3.2 API 参数错误

```python
# 后端定义
page_size: int = Query(default=20, le=200)  # 最大 200

# 前端请求
getList({ page_size: 500 })  # ❌ 超出限制，返回 422

# 解决方案
# 方案A：前端遵守后端约束
getList({ page_size: 200 })  # ✅

# 方案B：后端放宽限制（需要评估性能影响）
page_size: int = Query(default=20, le=1000)
```

### 3.3 选项/下拉数据联动

```javascript
// 问题：下拉选项是硬编码，没有和实际数据联动
const options = ['选项1', '选项2', '选项3']  // ❌ 硬编码

// 解决：从 API 动态获取
const options = ref([])
onMounted(async () => {
  const res = await getOptions()
  options.value = res.data.items  // ✅ 动态数据
})
```

### 3.4 组件 prop 类型错误

```javascript
// 问题：函数返回 undefined，组件 prop 验证失败
const getType = (value) => {
  const map = { 'A': 'success', 'B': 'warning' }
  return map[value]  // ❌ 未知值返回 undefined
}

// 解决：确保返回有效默认值
const getType = (value) => {
  if (!value) return 'info'  // 处理 null/undefined
  const map = { 'A': 'success', 'B': 'warning' }
  return map[value] || 'info'  // ✅ 提供默认值
}
```

```markdown

- [ ] 前端显示逻辑
```

## 五、调试技巧

### 5.1 后端调试

```python
# 在关键位置添加日志
import logging
logger = logging.getLogger(__name__)

@router.get("/")
async def get_items():
    logger.info("收到请求，参数: ...")
    try:
        result = await service.get_items()
        logger.info(f"返回 {len(result)} 条数据")
        return result
    except Exception as e:
        logger.error(f"处理失败: {e}", exc_info=True)
        raise
```

### 5.2 前端调试

```javascript
// API 响应拦截器中打印日志
instance.interceptors.response.use(
  response => {
    console.log('[API] 响应:', response.config.url, response.data)
    return response
  },
  error => {
    console.error('[API] 错误:', error.config?.url, error.message)
    return Promise.reject(error)
  }
)
```

### 5.3 快速定位问题的命令

```bash
# 检查后端是否运行
curl http://localhost:8000/health

# 测试特定 API
curl http://localhost:8000/api/v1/subjects/

# 检查数据库表结构
psql -U postgres -d scheduling -c "\d subjects"

# 查看后端实时日志
# (后端在 --reload 模式下会自动输出到终端)
```

## 六、AI 助手工作规范

### 6.1 接收任务时

```markdown
收到任务后，我会按以下步骤处理：

1. **理解需求**
   - 确认功能目标
   - 识别涉及的模块和文件
   - 评估可能的影响范围

2. **制定方案**
   - 列出需要修改的文件
   - 说明修改思路
   - 提示可能的风险

3. **分步执行**
   - 每次修改一个文件或一组相关文件
   - 每步完成后说明做了什么
   - 遇到问题时暂停并说明

4. **验证结果**
   - 提示需要测试的步骤
   - 说明预期效果
   - 询问是否有异常
```

### 6.2 诊断问题时

```markdown
当用户报告问题时，我会：

1. **收集信息**
   - 请求后端终端日志
   - 请求浏览器控制台错误
   - 请求具体的操作步骤

2. **分析顺序**
   - 先看后端日志（是否有 Python 异常）
   - 再看 HTTP 状态码（4xx/5xx 的含义不同）
   - 最后看前端逻辑

3. **不做假设**
   - 不假设"应该没问题"
   - 每个怀疑点都要验证
   - 从最可能的原因开始排查

4. **解释清楚**
   - 说明问题的根本原因
   - 解释为什么会出现这个错误
   - 提供解决方案和预防措施
```

### 6.3 代码修改时

```markdown
修改代码时，我会遵循：

1. **最小化修改原则**
   - 只修改必要的部分
   - 保持现有代码风格
   - 不做无关的"优化"

2. **向后兼容**
   - 考虑历史数据
   - 提供默认值
   - 使用容错处理

3. **完整性检查**
   - 修改 A 时考虑是否需要同步修改 B
   - 特别注意前后端联动的场景
   - 特别注意数据库与代码的同步

4. **清晰说明**
   - 说明修改了什么
   - 说明为什么这样修改
   - 说明用户需要做什么（如重启服务）
```

## 八、经验总结

### 8.1 我们踩过的坑

| 坑 | 原因 | 解决方案 | 预防措施 |
|----|------|---------|---------|
| CORS 错误实际是后端 500 | ORM 字段与数据库不同步 | 同步数据库或回滚代码 | 修改模型后立即同步数据库 |
| 422 参数校验失败 | 前端请求超出后端限制 | 调整前端参数或放宽后端限制 | 前后端参数约束文档化 |
| 数据不显示 | API 失败后 fallback 到 Mock | 确保 API 正常返回 | Mock 数据应有明显提示 |
| 下拉选项不联动 | 硬编码而非动态获取 | 改为 API 动态获取 | 所有选项数据都应动态化 |
| 组件 prop 类型错误 | 函数返回 undefined | 添加默认值处理 | 始终提供有效的默认值 |

### 8.2 好的实践

1. **文档先行**：先写清楚要做什么，再动手写代码
2. **小步快跑**：每次改一点，测一点，不要积累大量未测试的修改
3. **日志为王**：关键操作都要有日志，出问题时能快速定位
4. **防御性编程**：假设输入可能是错误的，处理各种边界情况
5. **向后兼容**：修改时考虑历史数据，提供平滑迁移路径

### 8.3 效率提升技巧

1. **并行开发**：不相关的功能可以同时进行
2. **模板复用**：相似模块使用统一模板，减少重复工作
3. **自动化测试**：关键功能写测试，避免回归问题
4. **代码审查**：AI 生成的代码要人工审查，理解后再合并
