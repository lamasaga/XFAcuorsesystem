# 排课系统双方向改造技术文档

> **版本**: v1.0  
> **日期**: 2026-05-13  
> **改造范围**: 方向A（时间槽配置化 + 跨学部教师约束）+ 方向B（A-Level 纳入排课引擎）

---

## 一、背景与核心问题

### 1.1 已确认的三个核心事实

1. **A-Level 与行政班排课是「双轨制」**：A-Level 课程靠 `CourseClass.schedule_pattern` 人工预定义时间，完全不参与 CP-SAT 求解器。学生个人课表是在展示层将行政班 `schedule_items` 与 A-Level `schedule_pattern` 内存拼接而成，**不检查任何冲突**。

2. **三学部时间槽各不相同**：小学部（周一 8:40 开始）、中学部（周一 8:30 开始）、高中部（周一 8:10 开始），且周五均提前至 15:40 放学。当前引擎只区分"常规9节/选修11节/周五8节"，**没有按学部分辨时间槽**。

3. **跨学部教师时间约束缺失**：同时教小学和中学的教师，其 `unavailable_slots` 按"节次编号"存储，但小学部的"第5节"（12:35-13:15）与中学部的"第5节"（11:40-12:20）是完全不同的时段。当前系统**按节次编号统一处理**，导致教师可用性判断错误。

### 1.2 改造目标

| 方向 | 目标 | 影响范围 |
|------|------|---------|
| **方向A** | 时间槽配置化 + 跨学部教师约束修复 | 所有学部 |
| **方向B** | A-Level 课程纳入 CP-SAT 自动排课 | 高中部 |

---

## 二、总体架构

### 2.1 改造前后对比

```
【改造前】
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│ 行政班数据   │────→│ CP-SAT求解器  │────→│ schedule_items│
│ (tasks)     │     │ (自动排课)    │     │ (行政班结果)  │
└─────────────┘     └──────────────┘     └──────┬──────┘
                                                 │
┌─────────────┐     ┌──────────────┐            │ 内存拼接
│ A-Level数据  │────→│ schedule_pattern│─────────┘
│ (CourseClass)│     │ (人工预定义)   │
└─────────────┘     └──────────────┘

【改造后】
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│ 行政班数据   │────→│ CP-SAT求解器  │────→│ schedule_items│
│ (tasks)     │     │ (Tier 1-3)   │     │ (行政班结果)  │
└─────────────┘     └──────────────┘     └──────┬──────┘
                                                 │
                                                 │ teacher_occupied
┌─────────────┐     ┌──────────────┐            │
│ A-Level数据  │────→│ AlevelSchedule │─────────┘
│ (CourseClass)│     │ Solver (CP-SAT)│        (统一存储)
└─────────────┘     └──────────────┘
```

### 2.2 核心设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| A-Level 排课方案 | **顺序排课**（行政班先 → A-Level 后） | 风险低、行政班逻辑零改动、可快速验证 |
| A-Level 结果存储 | **扩展 schedule_items** | 最小侵入，复用现有查询体系 |
| 教师不可用时间 | **加载时映射 + session_department** | 不改 DB 和前端，约束检查传入课程学部 |
| 时间槽配置 | **DB 表 time_slot_configs** | 支持未来灵活调整，71条数据覆盖三学部 |

### 3.4 教师可用性约束改造

**核心问题**：`Teacher.department="BOTH"` 的跨学部教师，其班次限制应根据**所教班级**的学部决定，而非教师自身属性。

#### `Teacher.is_available()` 改造

```python
def is_available(self, day: int, period: int, session_department: str = None) -> bool:
    """
    session_department: 当前课程的学部（用于跨学部教师的班次判断）
    """
    # 1. 检查手动不可用时间
    manual_unavailable = self.unavailable_slots.get(day, [])
    if period in manual_unavailable:
        return False
    
    # 2. 检查班次（使用 session_department 进行学部感知判断）
    shift_unavailable = self._get_shift_unavailable(day, session_department)
    if period in shift_unavailable:
        return False
    return True
```

#### `_get_shift_unavailable()` 改造

```python
def _get_shift_unavailable(self, day: int, effective_dept: str = None) -> List[int]:
    shift = self.daily_shifts.get(str(day), "morning")
    if shift == "evening":
        dept = effective_dept or self.department
        if dept == "PRIMARY":
            return [1, 2, 3, 4, 5]   # 小学部晚班：上午全部不可用
        else:
            return [1, 2, 3, 4]      # 中学部/高中部晚班：可排第5节
    return []
```

def _get_max_period(self, day: int, session: ScheduleSession) -> int:
    # 优先使用配置化的时间槽数据
    if self.data.time_slots and session.department in self.data.time_slots:
        return self.data.time_slots[session.department].get_max_period(day)
    
    # 回退到硬编码逻辑（向后兼容）
    if day == 5:
        return 8
    if day == 4 and session.grades and all(g in ('G8', 'G9') for g in session.grades):

    return 9

### 4.2 A-Level 数据加载

`DatabaseLoader._load_alevel_sessions()`：

1. 查询 `CourseClass`（状态 ACTIVE，未删除，有教师）
2. 查询 `CourseClassMember`（状态 ENROLLED）

5. 构建 `AlevelScheduleSession` 列表

### 4.3 A-Level 排课求解器

#### 核心设计

**求解模式**：顺序排课（行政班先排 → A-Level 后在剩余空闲时段中排课）

**文件**：`backend/app/engine/alevel_solver.py`

#### 输入

```python
AlevelScheduleSolver(
    data: ScheduleData,                    # 含 alevel_sessions 和 time_slots
    teacher_occupied: Dict[(tid, day, period), bool],  # 行政班教师占用
    student_occupied: Dict[(sid, day, period), bool],  # 行政班学生占用（可选）
    prefer_elective_slots: bool = True,    # 优先第10-11节
)
```

#### 约束体系

| 层级 | 约束 | 实现方式 |
|------|------|---------|
| 硬约束 H1 | 每个 session 恰好一个槽位 | `AddExactlyOne(vars_list)` |
| 硬约束 H2 | 教师不冲突 | `AddAtMostOne()` 同一教师同一时段 |
| 硬约束 H3 | 学生不冲突 | `AddAtMostOne()` 同一学生同一时段 |
| 硬约束 H4 | 教师时间可用 | `_build_available_slots()` 过滤 `teacher_occupied` |
| 软约束 S1 | 优先第 10-11 节（选修课时间） | 目标函数加权 +100 |
| 软约束 S2 | 其次第 8-9 节 | 目标函数加权 +50 |
| 软约束 S3 | 尽量避免周五 | 目标函数加权 -30 |

#### 求解流程

```
1. _build_available_slots()
   └─ 遍历 day=1~5, period=1~max_period
      └─ 过滤：教师被行政班占用 / 学生被行政班占用 / 超出时间槽范围

2. _create_variables()
   └─ 为每个 session 的每个可用 slot 创建 BoolVar

3. _add_constraints()
   └─ C1: 每个 session 恰好一个 slot
   └─ C2: 教师不冲突（teacher_id + day + period）
   └─ C3: 学生不冲突（student_id + day + period）

4. _add_objective()
   └─ 优先选修课时段（第10-11节 +100，第8-9节 +50）

5. Solve() → _extract_solution()
```

### 4.4 与行政班排课集成

#### `ScheduleEngine.run()` 改造

```python
# 行政班排课（现有流程）
solver = CPScheduleSolver(self.data)
solutions = solver.solve(...)

# A-Level 排课（新增）
alevel_records_map = {}
if self.data.alevel_sessions:
    for i, records in enumerate(solutions):
        teacher_occupied = self._build_teacher_occupied(records)
        alevel_solver = AlevelScheduleSolver(
            self.data,
            teacher_occupied=teacher_occupied,
        )
        alevel_records = alevel_solver.solve()
        alevel_records_map[i] = alevel_records

# 统一保存（行政班 + A-Level）
for i, records in enumerate(solutions):
    alevel_records = alevel_records_map.get(i, [])
    schedule_id = self._save_results(
        records, alevel_records, suffix, batch_id, score
    )
```

#### `_save_results()` 扩展

```python
def _save_results(self, records, alevel_records, suffix, batch_id, score):
    # 保存行政班（item_type="homeroom"）
    for r in records:
        ScheduleItem(
            item_type="homeroom",
            task_id=r.task_id,
            teacher_id=r.teacher_id,
            class_id=r.class_id,
            subject_id=r.subject_id,
            day=r.day, period=r.period,
            duration=r.duration,
        )
    
    # 保存 A-Level（item_type="alevel"）
    for ar in alevel_records:
        ScheduleItem(
            item_type="alevel",
            course_class_id=ar.course_class_id,
            teacher_id=ar.teacher_id,
            day=ar.day, period=ar.period,
            duration=ar.duration,
        )
```

### 4.5 查询层改造

#### `by-teacher` 改造

- 查询 `teacher_id` 的所有 `schedule_items`（含 homeroom + alevel）
- `homeroom`：从 `task_id`/`class_id`/`subject_id` 获取信息（现有逻辑）
- `alevel`：从 `course_class_id` 获取 `CourseClass` 和 `AlevelSubject` 信息

#### `by-student` 改造

- **Part 1（行政班）**：保持现有逻辑，从 `class_id` 查询 `schedule_items`
- **Part 2（A-Level）**：从 `schedule_items` 直接读取（`item_type="alevel"` + `course_class_id in enrolled_classes`）
- **冲突检测**：同一时段既有行政班又有 A-Level 时，标记叠加显示

### 4.6 自动分班 API

**端点**：`POST /api/v1/course-classes/allocate`

**参数**：
- `academic_year`：学年（默认 2025-2026）
- `semester`：学期（默认 FALL）
- `min_students`：最低开班人数（默认 5）

**算法流程**：

```
1. 查询所有 APPROVED 状态的选课记录
2. 按 alevel_subject_id 聚合学生
3. 对于每个科目：
   a. 获取 AlevelSubject 配置（max_students, weekly_hours）
   b. 查询现有 ACTIVE 课程班及其剩余容量
   c. 优先填满现有班级
   d. 剩余学生按 max_students 拆分为平行班
   e. 均匀分配学生
   f. 创建 CourseClass 和 CourseClassMember
4. 返回分班结果统计
```

**分班策略**：
- 现有班级容量足够 → 只补充学生，不建新班
- 现有班级容量不足 → 填满现有班级，剩余建新班
- 无现有班级 → 直接按容量拆分建新班

## 六、关键设计决策详解

### 6.1 为什么采用「顺序排课」而非「统一排课」？

| 维度 | 顺序排课（选定方案） | 统一排课 |
|------|-------------------|---------|
| 行政班影响 | 零改动 | 需大幅改造 SessionBuilder |
| A-Level 失败 | 不影响行政班 | 整个排课失败 |
| 实现复杂度 | 低（新增一个求解器） | 高（改造核心约束体系） |
| 最优性 | A-Level 只能"填缝" | 全局最优 |
| 求解时间 | 快（两轮独立求解） | 慢（变量数翻倍） |

**决策理由**：当前最紧迫的需求是让 A-Level 课程参与自动排课并检查冲突。顺序排课在 1-2 周内可验证上线，统一排课需要 1 个月以上且风险高。如果业务需要全局最优，可在顺序排课稳定后评估迁移。

### 6.2 为什么 `Teacher.is_available` 增加 `session_department` 参数而非修改数据结构？

- **不改数据结构**：`teachers.unavailable_slots` 保持 `{day: [periods]}` 格式，避免前端大规模改动
- **加载时映射**：在约束检查阶段，根据当前课程的学部动态判断班次规则
- **最小侵入**：只修改引擎内部逻辑，不影响现有 API 和前端

### 6.3 为什么 A-Level 结果也存 `schedule_items` 而非独立表？

- **复用查询体系**：`by-student`/`by-teacher`/`by-class` 等查询无需改造即可支持 A-Level
- **统一调课**：现有的调课 API（swap/move）只需少量改造即可支持 A-Level
- **简化架构**：避免维护两套平行的存储和查询逻辑
