## 二、核心技术详解

### 2.1 Vue 3 — 前端界面框架

**它是什么**: 一个用来构建网页用户界面的 JavaScript 框架。

**解决什么问题**: 没有它，你需要手动操作 HTML 元素来更新页面，代码会变得极其混乱且难以维护。比如"教师列表更新了，页面上的表格也要跟着变"——手动处理这种"数据变了→界面也要变"的逻辑非常痛苦。

**核心思想**: 数据驱动视图。你只需要修改数据，页面会自动更新。
> 类比：Vue 就像 Excel 的公式——当一个单元格的值变了，所有引用它的单元格会自动重新计算。你修改了"教师姓名"这个数据，页面上所有显示这个名字的地方都会自动更新。

**在本项目中**: 构建排课系统的全部页面——仪表盘、数据管理、自动排课引导、约束配置、课表展示、数据导出等 6 大页面模块。

**能力边界**:
- 擅长: 构建交互丰富的单页应用（SPA）、组件化开发、响应式数据绑定
- 不擅长: SEO 要求高的内容站点、极致首屏加载速度
- 常见误用: 在组件中直接修改 props（应该通过事件通知父组件）

---

### 2.2 FastAPI — 后端 API 框架

**它是什么**: 一个用 Python 编写的现代 Web 框架，专门用来创建 API 接口。

**解决什么问题**: 前端需要和后端"对话"——比如前端说"给我所有教师的列表"，后端需要一个"接话的人"来接收请求、查数据库、然后把结果返回。FastAPI 就是这个"接话系统"。

**核心思想**: 用类型注解自动完成验证和文档生成。
> 类比：FastAPI 就像一个高效的前台接待员——你告诉她"我要找姓王的老师"，她不仅会帮你查，还会先检查"姓王"这个条件格式对不对，查完后把结果整理好交给你。更妙的是，她会自动记录所有能办理的业务类型（自动生成 API 文档）。

**在本项目中**: 提供 30+ 个 API 接口，涵盖教师/班级/科目/任务/分层/场地/课表/统计等所有数据操作，以及排课引擎的触发入口。

**能力边界**:
- 擅长: 异步高性能 API、自动数据验证、自动生成交互式文档（Swagger UI）
- 不擅长: 服务端渲染页面、长时间后台任务（需配合 Celery 等）
- 常见误用: 在路由函数中写大量业务逻辑（应该分层到 service）

---

### 2.3 Google OR-Tools CP-SAT — 排课求解器

**它是什么**: Google 开发的开源运筹优化工具包中的约束满足求解器。

**解决什么问题**: 排课是 NP-Hard 问题（理论搜索空间达 10^100+），穷举法完全不可行。需要一个能在海量可能性中快速找到满足所有条件的解的"超级搜索引擎"。

**核心思想**: 将排课问题转化为数学模型——定义变量（每节课排在哪个时间段？）、约束（教师不能同时上两节课）和目标（主科尽量排上午），然后让求解器自动找到最优解。
> 类比：想象你在玩一个超复杂的数独——有 28 个班级、54 位教师、32 门科目，每个"格子"都有大量限制条件。CP-SAT 就像一个数独超级玩家，它能通过"约束传播"（填一个数就排除一大片可能性）和"智能回溯"（走错了就退回来换条路），在几秒到几分钟内找到答案。

**在本项目中**: 排课引擎的核心。接收所有教学任务和约束配置，通过数学建模求解，输出完整课表。支持 4 项物理硬约束 + 9 项可配置约束（Hard/Soft 可切换），还能在无解时自动诊断冲突源。

**能力边界**:
- 擅长: 约束满足问题、整数规划、组合优化、支持硬约束+软约束混合优化
- 不擅长: 连续优化问题、机器学习类任务
- 常见误用: 变量域设置过大导致搜索空间爆炸、忘记设置求解时间上限

---

### 2.4 SQLAlchemy — 数据库操作工具（ORM）

**它是什么**: Python 最流行的 ORM（对象关系映射）库，让你用 Python 代码操作数据库。

**解决什么问题**: 直接写 SQL 语句容易出错、不同数据库语法不同、代码和数据库强耦合。

**核心思想**: 把数据库表映射成 Python 类，把行映射成对象。
> 类比：如果数据库是一个 Excel 表，ORM 就像一个翻译官——你说"给我名字叫张三的教师"（Python 代码），翻译官帮你转成 Excel 能懂的话（SQL），再把查到的行变成你能直接用的 Python 对象。

**在本项目中**: 定义了 teachers、classes、subjects、teaching_tasks、layer_groups、venues、schedules、schedule_items、schedule_configs 等所有数据表模型。同时支持 PostgreSQL 和 SQLite 双数据库切换。

**能力边界**:
- 擅长: 标准 CRUD 操作、多数据库支持、关联查询、数据模型管理
- 不擅长: 极致性能的批量操作（此时应使用原生 SQL）
- 常见误用: 在循环中逐条查询数据库（应使用批量查询或 JOIN）

---

### 2.5 Electron — 桌面应用打包

**它是什么**: 一个用 Web 技术（HTML/CSS/JavaScript）构建跨平台桌面应用的框架。

**解决什么问题**: 排课系统需要分发给非技术人员使用，但让他们安装 Python、Node.js、PostgreSQL 是不现实的。需要一个"双击即用"的桌面程序。

**核心思想**: 把一个精简版的 Chrome 浏览器和你的 Web 应用打包在一起。
> 类比：Electron 就像一个移动餐车——它把整个"餐厅"（浏览器）和"菜品"（你的 Web 应用）打包在一辆车里，开到哪里都能直接营业，不需要顾客（用户）自己准备厨房。

**在本项目中**: 将 Vue 前端 + Python 后端打包为独立的 Windows/macOS/Linux 桌面应用。使用 SQLite 替代 PostgreSQL，实现零配置启动。

**能力边界**:
- 擅长: 跨平台桌面应用、复用 Web 技术栈、访问系统 API（文件、通知等）
- 不擅长: 资源占用较高（内存约 100MB+）、不适合做高性能桌面游戏
- 常见误用: 将过多逻辑放在主进程（应放在渲染进程或后端）

## 三、技术对比与选型

### 决策 1: 前端框架选择

**我们选了**: Vue 3
**备选方案**: React、Angular

| 维度 | Vue 3 | React | Angular |
|------|-------|-------|---------|
| 学习曲线 | 平缓，模板语法直观 | 中等，JSX 需适应 | 陡峭，概念多 |
| 生态与社区 | 丰富，国内社区强大 | 最丰富 | 较丰富，企业级 |
| 性能特点 | 优秀，编译时优化 | 优秀 | 良好 |
| 适用规模 | 中小到大型 | 任意规模 | 中大型企业级 |
| 与本项目契合度 | 极高 | 高 | 偏重 |

**选 Vue 3 的理由**: Element Plus 生态完善，适合管理系统；Composition API 功能强大；国内学习资源丰富；上手快，开发效率高。

**什么时候该选 React**: 如果团队已熟悉 React，或需要 React Native 做移动端，或项目需要更灵活的架构。

---

### 决策 2: 后端语言与框架

**我们选了**: Python + FastAPI
**备选方案**: Node.js + Express、Java + Spring Boot

| 维度 | Python + FastAPI | Node.js + Express | Java + Spring Boot |
|------|-----------------|-------------------|--------------------|
| 学习曲线 | 低，Python 语法简洁 | 低，前后端同语言 | 高，概念和配置多 |
| 生态与社区 | 丰富，算法/AI 生态顶级 | 丰富，npm 包海量 | 企业级最强 |
| 性能特点 | 异步高并发，接近 Node | 单线程事件循环 | 多线程，高稳定性 |
| 适用规模 | 中小型到中大型 | 中小型 | 中大型到超大型 |
| 与本项目契合度 | 极高 | 中等 | 偏重 |

**选 Python + FastAPI 的理由**: 排课核心是算法（OR-Tools 是 Python 原生库），Python 在数学/算法领域生态无可替代；FastAPI 自动生成 API 文档，开发效率极高；async/await 支持异步，性能不输 Node.js。

**什么时候该选 Node.js**: 如果项目不涉及复杂算法，前后端想用同一语言，或团队全是 JavaScript 开发者。

---

### 决策 3: 排课算法选择

**我们选了**: OR-Tools CP-SAT（约束满足求解器）
**备选方案**: DEAP（遗传算法）、自研启发式算法

| 维度 | OR-Tools CP-SAT | DEAP (遗传算法) | 自研启发式 |
|------|----------------|-----------------|-----------|
| 学习曲线 | 中等，需理解约束建模 | 中等，需理解遗传算法 | 高，需深厚算法功底 |
| 解的质量 | 极高，数学最优保证 | 较好，近似最优 | 取决于实现 |
| 约束处理 | 原生支持硬/软约束 | 需手动编码罚函数 | 需自行实现 |
| 可维护性 | 高，声明式添加约束 | 中，需调参 | 低 |
| 无解诊断 | 内建支持 | 无 | 需自建 |

**选 OR-Tools 的理由**: 排课是典型的约束满足问题，CP-SAT 天然契合；声明式约束添加，易于扩展新规则；内建无解诊断，便于排查冲突；Google 维护，稳定可靠。

**什么时候该选 DEAP**: 如果问题规模特别大（数千个班级）且可以接受近似解，或者约束条件难以用数学公式表达。

---

### 决策 4: 数据库选择

**我们选了**: PostgreSQL（主）+ SQLite（桌面模式）
**备选方案**: MySQL、MongoDB

| 维度 | PostgreSQL | MySQL | MongoDB |
|------|-----------|-------|---------|
| 学习曲线 | 中等 | 低 | 低（但设计不同） |
| JSON 支持 | JSONB 原生支持 | JSON 基本支持 | 天然文档型 |
| 数据完整性 | 最严格 | 良好 | 较弱 |
| ARRAY 类型 | 原生支持 | 不支持 | 天然支持 |
| 与本项目契合度 | 极高 | 高 | 中 |

**选 PostgreSQL 的理由**: 约束配置存储需要 JSONB（如 `config_json`）；教师可教科目需要 ARRAY 类型；数据完整性对排课系统至关重要。SQLite 作为桌面模式补充，通过 `USE_SQLITE` 环境变量切换。

**什么时候该选 MySQL**: 如果运维团队更熟悉 MySQL，或部署环境已有 MySQL 集群。

## 四、技术演变地图

### 前端框架的演变

```
jQuery (手动DOM操作) → Angular 1.x (双向绑定) → React/Vue 2 (虚拟DOM+组件化) → Vue 3/React 18 (组合式API+编译优化) → [趋势] 信号(Signals)模式
```

每次迁移的驱动力：手动 DOM 操作太痛苦 → MV* 模式解决了，但性能差 → 虚拟 DOM 兼顾了性能和开发体验 → Composition API 解决了大型组件的逻辑复用难题

### Python Web 框架的演变

```
CGI → Django (全能型) → Flask (轻量级) → FastAPI (异步+类型+高性能) → [趋势] 更深度的异步生态
```

每次迁移的驱动力：CGI 太原始 → Django 全家桶太重 → Flask 灵活但缺乏验证和文档 → FastAPI 用类型注解一站式解决了验证、文档、性能问题

### 排课算法的演变

```
人工排课 → 简单贪心/回溯 → 遗传算法/模拟退火 → 约束满足(CP-SAT)/整数规划 → [趋势] AI辅助+约束求解混合
```

每次迁移的驱动力：人工排不动了 → 简单算法解质量不稳定 → 启发式算法难调参 → 约束求解器提供了数学最优保证和声明式建模

### 桌面应用的演变

```
原生开发(C++/C#) → Java Swing → Adobe AIR → Electron (Web技术) → Tauri (Rust+Web，更轻量) → [趋势] Tauri 2.0
```

每次迁移的驱动力：原生开发跨平台成本高 → Java 界面丑 → AIR 被弃 → Electron 让 Web 开发者能做桌面应用 → Tauri 解决了 Electron 内存占用大的问题

## 五、架构模式解读

**本项目采用**: 前后端分离 + 模块化单体架构

**核心思想**: 前端和后端是两个独立的项目，通过 HTTP API 通信。后端内部按业务领域划分模块，每个模块自成体系。
> 类比：就像一家餐厅——前厅（前端）负责接待顾客、展示菜单、传递订单；后厨（后端）负责做菜。前厅和后厨通过"传菜口"（API）沟通。后厨内部又分成不同的档口（模块）：炒菜区（教师管理）、面点区（班级管理）、甜品区（排课引擎）……每个档口有自己的原料（models）、菜谱（schemas）、厨师（service）和接单窗口（router）。

**代码中的体现**:

| 目录 | 对应角色 |
|------|---------|
| `frontend/src/views/` | 前厅各区域（页面） |
| `frontend/src/api/` | 传菜口的"对讲机"（API 调用） |
| `backend/app/modules/teachers/` | 后厨的"教师管理档口" |
| `backend/app/modules/schedules/` | 后厨的"课表管理档口" |
| `backend/app/engine/` | 后厨的"核心主厨"（排课引擎） |
| `backend/app/core/` | 后厨的"公共设施"（配置、数据库连接） |

**这个模式的权衡**:
- 好处: 前后端可独立开发和部署；模块边界清晰，改一个模块不影响其他模块；技术栈可以分别选择最合适的
- 代价: 需要定义和维护 API 契约；前后端联调有成本；数据需要序列化/反序列化
- 何时不适用: 极简的小工具（直接用全栈框架更快）、需要超高实时性的场景（WebSocket 更合适）

## 六、协作关系图

```
用户操作浏览器
     │
     ▼
 Vue 3 前端 (Vite 开发 / Electron 桌面)
     │  Axios HTTP 请求
     ▼
 FastAPI 后端 (Uvicorn 服务器)
     │
     ├──→ 业务模块 (teachers/classes/subjects/tasks/layers/venues)
     │         │
     │         ▼
     │    SQLAlchemy ORM ──→ PostgreSQL / SQLite
     │
     └──→ 排课引擎 (engine/)
               │
               ├── DataLoader: 从数据库加载教学任务、约束配置
               ├── SessionBuilder: 将任务拆分为排课会话
               ├── CP-SAT Solver: Google OR-Tools 约束求解
               │     ├── 物理硬约束 (H1-H4)
               │     ├── 可配置约束 (R1-R9, Hard/Soft)
               │     └── 目标函数 (最小化软约束违反)
               └── ResultSaver: 将求解结果写回数据库
```

**数据流详解**:

1. **数据录入流**: 用户在前端页面录入教师/班级/科目/任务 → API 请求 → FastAPI 路由 → CRUD 操作 → 存入数据库
2. **排课流**: 用户点击"开始排课" → API 触发 `ScheduleEngine.run()` → 加载数据 → CP-SAT 建模求解 → 保存结果 → 返回前端展示
3. **查看课表流**: 用户选择班级/教师/教室视图 → API 查询 → 从 schedule_items 表读取 → 前端渲染课表网格
4. **手动调课流**: 用户拖拽课程 → API 发送 swap/move 请求 → 后端校验冲突 → 更新数据库 → 前端刷新

## 七、学习路线建议

### 1. 已通过本项目接触到的技术

- **前端**: Vue 3 (Composition API + `<script setup>`)、Vue Router、Pinia 状态管理、Element Plus UI 组件库、Axios HTTP 通信、Vite 构建工具、Sass 预处理器
- **后端**: Python 3.10+、FastAPI (RESTful API)、SQLAlchemy 2.0 (ORM)、Pydantic 2.0 (数据验证)、Uvicorn (ASGI 服务器)
- **算法**: Google OR-Tools CP-SAT (约束满足求解)、整数规划建模
- **数据库**: PostgreSQL (关系型数据库)、SQLite (嵌入式数据库)
- **桌面**: Electron (跨平台桌面应用)
- **工程化**: 前后端分离架构、模块化设计、API 设计规范

### 2. 建议下一步了解

- **TypeScript**: 本项目前端使用 JavaScript，但 TypeScript 能提供类型安全，减少运行时错误。对于项目规模增长后的可维护性非常有帮助。
- **Docker**: 本项目已有部署指南但尚未实际配置。Docker 能让"在我机器上能跑"变成"在任何机器上都能跑"，是现代部署的必备技能。
- **自动化测试 (pytest + Vitest)**: 本项目目前缺少测试覆盖。学会写测试，能让你在修改代码时更有信心——"改了不会坏"。

### 3. 中期可以探索

- **Redis 缓存**: 当并发用户增多时，可以用 Redis 缓存频繁查询的数据（如教师列表），显著提升响应速度。项目架构设计中已规划但尚未引入。
- **Alembic 数据库迁移**: 当前修改数据模型后需要手动执行 SQL，Alembic 能自动追踪模型变化并生成迁移脚本，是 SQLAlchemy 的标配伴侣。
- **CI/CD (GitHub Actions)**: 自动化构建、测试和部署流水线。每次推送代码后自动运行测试、自动构建桌面安装包，告别手动操作。
- **WebSocket 实时通信**: 排课过程可能耗时较长，用 WebSocket 可以将求解进度实时推送到前端，替代当前的轮询方式。
